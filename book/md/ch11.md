# 第十一章 推理引擎——AI如何像专家一样思考

本章将回答一个核心问题：

当前面已经建设好了本体中心、数据中心、知识中心、知识图谱和规则中心之后，AI究竟如何把这些能力组织起来，完成一次真正的分析、判断和决策？

推理引擎，就是整个数字底座的大脑。

## 一、为什么数据、知识和规则都有了，AI还是不会分析

自此已经完成了第一步建设：

数据中心能够查询业务数据；

知识中心能够检索制度和案例；

规则中心能够校验审批规则；

知识图谱能够关联对象关系。

但当秘书长提出一个问题时，例如：“为什么今年企业捐赠下降？”

AI仍然可能直接给出一堆建议。

真正的问题不是知识不够，而是没有分析过程。

真正的专家不会直接回答，而是会先提出一系列问题：

下降了多少？

是哪些企业下降？

是哪些项目受到影响？

与去年相比变化在哪里？

是行业变化，还是自身原因？

有没有违反制度？

有没有类似历史案例？

这就是推理。

推理引擎不是增加新的知识，而是组织整个分析过程。

## 二、推理引擎到底是什么

不要再讲概念，直接讲职责。

例如：

推理引擎负责五件事情：

① 理解问题

例如：

为什么筹款下降？

转换成：

分析对象：企业捐赠分析目标：寻找下降原因输出：原因分析+改进建议

这一步就是：

Task Planning（任务规划）

② 制定分析计划

不是马上查数据库。

而是先制定：

第一步 查询事实第二步 查询历史第三步 查询制度第四步 查询案例第五步 综合分析

这个就是：Execution Plan（执行计划）

![书中插图](/book/images/fig-22.jpg)

③ 调度各种能力

Execution Plan出来以后，推理引擎开始调用。

例如：

数据中心↓知识中心↓规则中心↓知识图谱↓Python分析↓LLM总结

注意：这里建议加入Python分析。

例如：

统计：

企业数量变化项目变化区域变化同比变化趋势分析聚类分析

这一步，不是LLM完成，而是：Python完成。

LLM负责解释。

这就是目前企业AI真正的实现方式。

## 三、推理引擎如何一步一步工作

例如：

用户：

分析环保项目延期原因

推理引擎：

第一步：识别对象

ProjectHospitalBudgetSupplier

第二步：生成执行计划

需要：预算、合同、付款、验收、项目日志

第三步：调用数据中心

SQL、API、向量检索

第四步：调用知识中心

找到：延期案例、项目制度

第五步：调用规则中心

检查：预算规则、审批规则、采购规则

第六步：Python分析

例如：

延期时间统计延期原因分类医院分布供应商分析甘特图趋势图

第七步：LLM综合推理

最终输出：

根因影响风险建议

## 四、推理计划（Reasoning Plan）——AI先制定计划，再开始分析

很多人认为，AI收到问题后就会立即开始回答。

实际上，一个真正的企业级推理引擎，并不会马上生成答案，而是先制定一份推理计划（Reasoning Plan）。

这就像一位经验丰富的秘书长接到一个复杂问题时，不会立刻下结论，而是先想清楚：

这个问题需要分析哪些对象？

需要收集哪些数据？

需要查询哪些制度？

需要参考哪些历史案例？

需要调用哪些分析工具？

最终需要输出什么结果？

推理计划，本质上就是AI的一份"工作计划"。

例如，秘书长提出：

"请分析环保项目延期的原因，并提出改进建议。"

推理引擎首先不会调用大模型回答，而是生成一份执行计划。

{  "task": "分析环保项目延期原因",  "goal": "找出延期原因并提出改进建议",  "objects": [    "Project",    "Supplier",    "Budget",    "Contract"  ],  "steps": [    "识别分析对象",    "获取项目执行数据",    "统计延期情况",    "查询历史延期案例",    "验证采购审批规则",    "分析供应商履约情况",    "生成原因分析",    "形成整改建议"  ],  "tools": [    "SQL查询",    "知识检索",    "规则引擎",    "Python统计分析"  ],  "output": [    "延期原因",    "影响分析",    "风险提示",    "整改建议"  ]}

有了这份计划之后，推理引擎才开始逐步执行，而不是想到哪里回答到哪里。

例如：

用户提出问题        │        ▼生成 Reasoning Plan        │        ▼调用数据中心        │        ▼调用知识中心        │        ▼调用规则中心        │        ▼调用分析工具        │        ▼综合推理        │        ▼生成最终结论

未来，推理计划不仅用于指导AI执行，也能够展示给用户查看。

用户可以清楚看到：

AI准备分析哪些内容？

为什么调用这些数据？

为什么需要这些规则？整个分析过程将变得更加透明、更加可信。

因此，推理计划并不是一句Prompt，而是一份可执行的分析方案（Execution Plan）。它决定了AI先做什么、后做什么、如何验证，以及最终如何形成结论。

## 四、推理引擎如何避免AI幻觉

这一节非常重要，也是所有使用AI-LLM最关心的。

推理引擎不是：

LLM自己想

而是：每一步都有依据。

例如：

事实↓知识↓规则↓关系↓Python验证↓最终回答

每一个结论都必须说明：

来自：哪个系统哪个制度哪个案例哪条规则

这样AI才能解释：为什么这样判断？企业才能真正使用。

**所以必要的话可以输出推理轨迹——让AI的每一个结论都有依据**

例如，AI回答：

"建议延期项目调整采购流程。"

为什么？依据是什么？引用了哪些制度？分析了哪些数据？

如果无法解释，企业就很难真正信任AI。

因此，推理引擎除了输出结果之外，还需要保存完整的推理轨迹（Reasoning Trace）。

所谓推理轨迹，就是AI在分析过程中留下的一条完整证据链。
